Dayforce API Integration

Keplr Vision · March 2025 to July 2026

Summary

I designed and owned a production Dayforce-to-Databricks integration that replaced a constrained custom-report, CSV, SFTP, and Azure Blob Storage workflow with reusable OAuth-authenticated API ingestion. The framework initially supported approximately 20 endpoints, handled complex endpoint parameter and key patterns, loaded history back to January 1, 2024, and enabled endpoint-specific full rebuilds alongside incremental processing. Its data later supported automated user provisioning and expanded workforce reporting in Power BI.

This was the first Keplr Vision project for which I had full ownership. I learned the Dayforce API structure, authentication model, endpoint requirements, and UI configuration from the Dayforce Developer Network documentation, gathered the business requirements for which data to extract, and designed both the reusable API class and the Databricks notebook that used it.

Context and problem

Workforce data was retrieved through custom reports built in the Dayforce UI, exported as CSV files, transferred through an SFTP client, and stored in Azure Blob Storage. Adding a column meant one of the few employees familiar with the report configuration had to modify it, and every new data request meant another report, export, and downstream pipeline.

The API integration removed that dependency and made new endpoints easy to add. Incremental processing also made it practical to refresh several times a day when the business wanted more frequent reporting.

Architecture

What I built

API framework

  • A reusable custom class for OAuth-authorized Dayforce connections, with endpoint functions designed so new endpoints can be added without rebuilding the connection framework.
  • Support for calls by date range, by cross-reference code, and through nested outer-key and inner-key relationships, including splitting date ranges that exceed an endpoint's maximum.
  • Concurrent calls through a thread pool with eight execution channels and centralized rate limiting.
  • A development-only validation class that tested individual GET and POST calls and surfaced structural errors immediately: invalid date ranges, wrong parameter names, malformed URLs. It was not part of the production runtime.

Databricks ingestion and operations

  • Delta tables with history back to January 1, 2024, merge behavior that tolerates schema evolution as Dayforce adds columns, and handling for all-null fields that PySpark would otherwise infer as void columns.
  • Hash-based audit identifiers for endpoints whose views do not guarantee primary keys, and source comparison to remove records no longer present where required.
  • Idempotent processing: a dropped table, a newly added endpoint, or a requested rebuild triggers a full load for that endpoint only, while the rest continue incrementally. Full-load-only endpoints, such as department details for more than 4,000 departments, are supported.
  • A scheduled Databricks Job four times per day, finishing in about one to two hours, with a two-hour termination limit, duration warnings, job parameters for special runs, targeted retries for specific HTTP status codes, endpoint-specific diagnostics for fragile endpoints, and failure notifications.

Ownership

Personally designed and authored

  • The API architecture, endpoint strategy, and ingestion requirements.
  • The reusable OAuth client class, the validation class, and the Databricks notebook that ran the process.
  • The Delta Lake merge, audit-identifier, deletion, and idempotent rebuild design.
  • Multiple iterations that took an initially buggy first version to reliable production operation.

AI-assisted, under my direction and review

  • Claude Code later helped refactor endpoint functions onto a shared executor implementation, reducing complexity and improving return consistency.
  • Claude Code also helped strengthen retry handling and endpoint-specific failure handling.
  • It did not originate the architecture or the initial implementation.

Status and boundaries

Production integration

  • The initial scope was approximately 20 endpoints chosen from a larger API surface; not every available endpoint was implemented, and not every endpoint supported incremental ingestion.
  • I have not quantified the time or cost reduction against the old export workflow, so I do not claim one.
