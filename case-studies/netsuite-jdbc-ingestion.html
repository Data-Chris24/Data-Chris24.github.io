NetSuite JDBC Ingestion Framework

Keplr Vision · March 2025 to July 2026

Summary

I designed a development-stage Databricks ingestion framework for extracting large, wide, and sensitive NetSuite datasets through a custom JDBC connection I created in Unity Catalog with OAuth 2.0 machine-to-machine authentication. The design used row-and-column tiling, controlled concurrency, incremental loading, and restartable CLOB backfills to reduce NetSuite server load. In testing, it extracted nearly 700,000 rows and approximately 150 columns, excluding four CLOB columns, in about 10 minutes before backfilling the memory-intensive fields separately.

Context and problem

I first prototyped a reusable NetSuite API class, then found that large, wide target tables caused silent server-side failures. Some targets held more than 2 million records, and more than 2,600 tables were available. A conventional JDBC approach failed the same way. The managed Databricks NetSuite connector lacked the OAuth 2.0 connection required for the critical sensitive data. So I created a custom JDBC connection in Unity Catalog, using the NetSuite-provided JDBC JAR, that accepts runtime configuration and lets an OAuth authorization string be injected dynamically.

Architecture

What I built

OAuth 2.0 machine-to-machine design

  • A security certificate uploaded to NetSuite and a NetSuite integration configured for the machine-to-machine token flow.
  • A JWT for the token endpoint that returns a 60-minute OAuth access token.
  • Source secrets in Azure Key Vault read through Databricks secret scopes, and the resulting token stored through a secret scope so it is redacted from notebook output and logs.
  • A reusable token function that checks whether a refresh is needed and requests a new token only after expiration, then injects the authorization string into the JDBC connection at runtime.

Tiled extraction

Large row counts and wide schemas kept overloading the connection. The strategy divides queries across bounded sets of rows and columns, includes the record ID in every column tile so results can be reconstructed, queries tiles concurrently, reassembles complete records on the Databricks side, and shifts compute to Databricks while reducing the response burden on NetSuite. Default tiling spreads a table's columns across eight channels, caps each tile at 50 columns including the ID, and allows up to 500,000 rows per row tile.

CLOB backfill and recoverability

CLOB fields were isolated from the main tiled load so they could not destabilize otherwise efficient extraction. A separate backfill loads the four CLOB columns one column and 1,000 rows per request, and resumes after an interruption instead of restarting the whole extraction.

Metadata-driven configuration and incremental loads

  • A configuration table with an active flag for integration selection, maximum concurrent connections, rows per tile, column-exclusion lists, and other table-specific settings.
  • Initial loads designed for an environment with data back to at least 2013 covering more than 250 practices; incremental loads using a last-modified field, when available, to select rows newer than the prior run.
  • A metrics table tracking prior run information as a foundation for data-quality checks and operational visibility. Test incremental extractions generally finished within a few minutes or seconds for the tables evaluated.

Status and boundaries

Development stage, not deployed to production

  • The framework was being tested in the development environment when I left. Connection, setup, bronze-ingestion, token-management, tiling, and CLOB-backfill notebooks were implemented.
  • The transaction table, which spans more than four transaction types, showed an additional anomaly whose root cause and fix were not completed.
  • No formal production validation or reconciliation framework was completed; the metrics table is development-stage run tracking, not a production observability platform.
  • Intended downstream uses (Encompass-to-NetSuite journal entries, procurement-request automation, Power BI trial-balance reporting, inventory visibility) are intentions, not realized outcomes of this framework.
