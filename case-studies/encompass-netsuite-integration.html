Encompass to NetSuite Financial Integration

Keplr Vision · Built from June 2025, production-ready September 2025, maintained through July 2026

Summary

I designed and built the production-ready financial integration for practices adopting Encompass by Eyefinity, transforming daily Snowflake source data through more than 40 Databricks tables into balanced NetSuite journal-entry payloads. The manually initiated monthly process handled more than 100,000 journal-entry lines across 18 practices using Spark Declarative Pipelines, Python, SQL, and an eight-lane REST API submission process. It became the only mechanism for moving Encompass transaction activity into NetSuite when the first practices launched in September 2025.

Context and problem

This was a new process created specifically for the Encompass by Eyefinity practice-management system. There was no predecessor manual journal-entry workflow to automate. I designed the integration from test data so that every practice adopting Encompass could transfer its financial activity into NetSuite. Supported transaction domains were inventory, sales, returns, payments, insurance payments, insurance-claim adjustments, and patient credits.

About three months after operational use began, the Revenue Cycle Management team redesigned parts of its Encompass workflow and changed transaction-type codes, so the affected business mappings and transformation logic had to be evaluated and remapped. The integration did not reach complete source coverage because Keplr was still working with Eyefinity to obtain data for certain transaction types.

Architecture

What I built

Journal-entry construction

  • One journal entry per practice per day, plus a separate transfer journal entry when balanced lines crossed locations and could not be split into independent location entries.
  • Each NetSuite payload carried top-level location, subsidiary, date, and related metadata plus a lines array; each line mapped to the right general-ledger account and debit or credit treatment from transaction type and business rules, with memos and descriptions for auditability.
  • Encompass office codes resolved through a three-character location code to the NetSuite location, and attributes on the NetSuite location object resolved subsidiaries and tax accounts. Some mappings reflected accounting treatment rather than one-to-one categories, for example insurance-type discounts posting as contractual adjustments.

Controls, operations, and security

  • A generated external journal-entry ID and a validation job that aggregated each entry to verify total debits equaled total credits before anything was submitted.
  • Source transaction identifiers and streaming-pipeline processing prevented duplicate postings; deleted and voided Encompass records were filtered out first.
  • A payload-source dataset for Accounting review and a required Accounting approval before I pushed entries through the API, plus an enriched dataset that recreated the Encompass flash-sales report to compare amounts at the start and end of the transformation.
  • Post-submission retrieval of each entry's NetSuite metadata by external ID, logged with internal ID, reference number, and creation time. Logic to delete and resubmit entries when recovery required it. Pipeline failures emailed; retries were performed manually.
  • Credentials in Azure Key Vault accessed through Databricks secret scopes, and OAuth tokens stored through a Databricks secret so they never appeared in output or logs.

Ownership

Personally designed and authored

  • The complete technical implementation: pipelines, transformations, mappings, balance checks, payload construction, API concurrency, security handling, and the tracking process.
  • Detailed mapping sessions with Accounting and business stakeholders to define transaction treatment and general-ledger accounts.
  • The evaluation and remapping work after the RCM team changed transaction codes.

AI-assisted

  • None. I wrote all of the implemented code before adopting AI coding assistants.
  • I had planned a Claude Code production-readiness review and further automation, but no AI-generated code was part of the project described here.
  • Accounting owned final reconciliation and validation decisions; I built the datasets and controls that supported their review.

Status and boundaries

Operational from September 2025, manually initiated monthly

  • The pipeline was technically designed for daily execution but was run and reviewed monthly, with an Accounting approval gate, when I left. Planned daily execution, automated retries, and row-level submission tracking were not completed.
  • It enabled a brand-new Encompass-to-NetSuite capability. It did not replace a prior manual journal-entry process, so I do not claim time savings or error reduction against one.
  • Coverage was not complete while Eyefinity source-data gaps remained for certain transaction types.
